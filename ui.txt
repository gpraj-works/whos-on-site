# Why I like this order

The original plan puts real-time/background processing before the full frontend experience. But from an implementation perspective, I'd rather do:

```text
Backend foundation
       ↓
Backend business logic
       ↓
Frontend foundation
       ↓
Frontend business workflow
       ↓
Real-time
       ↓
Background processing
       ↓
Production hardening
```

Because otherwise we could spend significant time building Socket.io events without having a UI that actually consumes them.

Instead:

### First make this work

```text
Dispatcher
   ↓
Create Job
   ↓
Assign Technician
   ↓
Change Status
   ↓
Database
```

Then:

### Make it real-time

```text
Dispatcher
   ↓
Assign Technician
   ↓
Database
   ↓
Socket.io
   ↓
Technician UI updates immediately
```

Then:

### Make it asynchronous

```text
Job assigned
   ↓
Database
   ↓
Event
   ├── Socket.io → UI
   │
   └── BullMQ → notification worker
```

That's a much more natural progression.
